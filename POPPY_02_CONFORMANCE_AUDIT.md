## Why there is no initial /messages request, and how the event arrives

[§7.2–7.3](https://personalagentprotocol.org/docs/0.2/spec#sending-messages) starts a conversation by sending its **first message** to `POST {endpoint}`. Only subsequent messages use `POST {endpoint}/{id}/messages`. `availability_client.py:8–17` does exactly that: initial subscription uses `start`, cancellation or a subsequent message with a conversation ID uses `send`. Absence of `/messages` during initial subscription is not a defect.

Recorded actual HTTPS/Chrome fixture (`evidence/visible-poppy-messages.json`, 01:58–01:59 UTC):

1. Thread → FORME `POST /poppy/conversations?wait=0`, JSON `message.sender=agent`, `message.data.forme_availability.action=subscribe`; FORME replies **201** with conversation ID, events, cursor, status and responder.
2. Thread opens `GET /poppy/conversations/{id}/events`, `Accept: text/event-stream`, Authorization DPoP and proof; FORME replies **200** and keeps sending frames.
3. FORME → Thread sends `id: evt_…` and `data: {"id":"evt_…","created_at":"…Z","type":"message","message":{"id":"restock_…","role":"company","sender":"agent","text":"Red Leather Court Sneakers is now available at FORME.","data":{"forme_availability":{"action":"available","watch":{…}}}}}`.
4. Reconnect GET carries `Last-Event-ID`; recorded three GETs and one initial POST. There is no callback `POST /event`, nor a required named SSE `event: availability`. The JSON event type is `message`; custom availability data is inside it. This matches [§7.5–7.6](https://personalagentprotocol.org/docs/0.2/spec#streaming).

Trace presentation captures response frames but labels the overall exchange `Thread server → FORME → Thread server`; it does not show each incoming frame as a separate direction row. This is a presentation limitation, not a different wire protocol. The source screenshot is `evidence/visible-poppy-restock-event.png`; authentication material is masked. Evidence is an isolated fixture, not proof of a new live subscription.

Consent ID ties the approved watch to stored customer/filter state; it is not protocol authorization or a secret. `availability:watch` is a declared custom OAuth scope. Stock changes are synthetic. `/storefront.json` is an app convention; browser activation comes only from `web.browser_session_endpoint`.
